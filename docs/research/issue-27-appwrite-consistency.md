# Transactions Appwrite et pagination `listDocuments`/`listRows` pour l'issue #27

**Recherche arrêtée le 5 novembre 2026.** Cette note distingue les faits publiés (documentation, code source officiel) des hypothèses; elle ne constitue pas une recommandation d'implémentation figée pour `functions/market-conversations`. Contexte : l'issue #27 (« Conversations achats et ventes ») demande qu'accepter une offre réserve l'annonce et rejette automatiquement les autres demandes en attente — une écriture qui touche potentiellement plusieurs documents (l'annonce, l'offre acceptée, les offres concurrentes) depuis un seul handler de Function.

## Conclusion

**Oui : Appwrite expose une véritable Transactions API côté base de données**, disponible sur Appwrite Cloud (y compris le plan Free utilisé par ce projet, cf. [ADR 0003](../adr/0003-hebergement-mvp-appwrite-francfort.md)) depuis Appwrite 1.8.0, et déjà supportée par les SDK installés dans ce dépôt (`node-appwrite@29.1.0` côté fonction, `appwrite@28.1.0` côté client — aucune mise à jour de dépendance nécessaire). Un handler de `market-conversations` peut créer une transaction, y mettre en file (« stage ») la mise à jour de l'annonce (→ réservée), la mise à jour de l'offre acceptée et la mise à jour groupée des offres concurrentes (→ refusées), puis **commit** une seule fois : Appwrite applique soit tout, soit rien (« If any operation fails, none are applied. Everything is rolled back. », [annonce Appwrite](https://appwrite.io/blog/post/announcing-transactions-api)). C'est le mécanisme pertinent pour « réservation + rejet des demandes en attente ».

Deux réserves importantes :
- **Le périmètre est limité aux écritures de lignes/documents** (create/update/upsert/delete, y compris en masse, plus les opérations numériques atomiques) sur TablesDB/DocumentsDB/VectorsDB ([doc Transactions](https://appwrite.io/docs/products/databases/tablesdb/transactions)). Il ne couvre ni Storage, ni Messaging, ni le déclenchement d'autres Functions, ni les changements de schéma — l'« atomicité du handler » n'est garantie que pour la séquence d'écritures BDD qu'il met lui-même dans la transaction.
- **La détection de conflit est optimiste, pas un verrou posé au moment du `stage`** : au commit, Appwrite compare l'horodatage `$updatedAt` courant de chaque document à l'instant où l'opération a été mise en file; en cas de modification externe entre-temps, le commit entier échoue avec `transaction_conflict` (HTTP 409) et rien n'est appliqué ([source `Update.php`](https://github.com/appwrite/appwrite/blob/30d6d252a726e74e9d3cd0ac1d10e8b0cddf731f/src/Appwrite/Platform/Modules/Databases/Http/Databases/Transactions/Update.php)). Le handler doit donc prévoir une relecture/nouvelle tentative sur ce code d'erreur, plutôt que supposer un succès immédiat.

Côté pagination, `listDocuments`/`listRows` retourne **25 éléments par défaut**, ajustable via `Query.limit()`; **aucune limite maximale n'est documentée**, mais la documentation prévient explicitement que de grandes pages dégradent les performances ([doc pagination](https://appwrite.io/docs/products/databases/documentsdb/pagination)). Pour un fil de conversation qui mélange offres et messages et grossit en continu, la documentation recommande la **pagination par curseur** (`Query.cursorAfter()`/`Query.cursorBefore()`) plutôt que par décalage (`Query.offset()`), précisément pour les collections à forte fréquence d'écriture comme un historique de chat, car le décalage peut alors faire apparaître des doublons ou sauter des résultats sous écritures concurrentes.

## Transactions : fonctionnement, limites et erreurs

**Cycle de vie.** `createTransaction([ttl])` renvoie un objet transaction (`$id`); ce `transactionId` est ensuite passé aux appels standards `createRow`/`updateRow`/`upsertRow`/`deleteRow` (et leurs variantes en masse `createRows`/`updateRows`/`upsertRows`/`deleteRows`), ou regroupé via `createOperations(transactionId, operations[])`. Les opérations sont mises en file côté serveur mais **non appliquées** tant que la transaction n'est pas validée. `updateTransaction(transactionId, { commit: true })` déclenche la validation de toutes les opérations (permissions, schéma, révisions) puis leur application atomique; `{ rollback: true }` ou l'expiration les annule ([doc Transactions](https://appwrite.io/docs/products/databases/tablesdb/transactions); [annonce Appwrite](https://appwrite.io/blog/post/announcing-transactions-api)). Les lectures (`listRows`/`getRow`) acceptent elles aussi un `transactionId` pour lire ses propres écritures non encore commitées.

**Limites et durée de vie.** Chaque transaction a un TTL configurable entre 60 secondes et 1 heure, par défaut 5 minutes (`APP_DATABASE_TXN_TTL_MIN/MAX/DEFAULT`, [constantes source](https://github.com/appwrite/appwrite/blob/30d6d252a726e74e9d3cd0ac1d10e8b0cddf731f/app/init/constants.php)); passé ce délai, la transaction est nettoyée automatiquement et ne peut plus être commitée ni enrichie. Le nombre d'opérations par transaction est plafonné selon le plan : **Free = 100 opérations** (correspond à `APP_DATABASE_TXN_MAX_OPERATIONS = 100` dans le même fichier), Pro = 1 000, Scale = 2 500 ([doc Transactions](https://appwrite.io/docs/products/databases/tablesdb/transactions)). Le plan Free, confirmé pour ce projet par l'[ADR 0003](../adr/0003-hebergement-mvp-appwrite-francfort.md), suffit largement pour « réserver + rejeter les offres en attente » sauf cas extrême (une annonce avec des dizaines d'offres simultanées).

**Autorisation.** Créer/committer une transaction exige le scope `documents.write`/`rows.write` et est ouvert aux types d'authentification `ADMIN`, `KEY`, `SESSION`, `JWT` ([source `Create.php`](https://github.com/appwrite/appwrite/blob/30d6d252a726e74e9d3cd0ac1d10e8b0cddf731f/src/Appwrite/Platform/Modules/Databases/Http/TablesDB/Transactions/Create.php)) — une Function serveur authentifiée par clé API (`AuthType::KEY`) peut donc créer et committer des transactions, ce qui correspond au pattern envisagé pour `market-conversations`. Les vérifications de permission par document restent appliquées au commit, hors du périmètre « skip authorization » interne réservé à la gestion propre de la transaction : une opération staged qui violerait les permissions du document cible lève une `AuthorizationException`, capturée pour marquer la transaction en échec plutôt que silencieusement ignorée ([source `Update.php`](https://github.com/appwrite/appwrite/blob/30d6d252a726e74e9d3cd0ac1d10e8b0cddf731f/src/Appwrite/Platform/Modules/Databases/Http/Databases/Transactions/Update.php), lignes ~144–403).

**Codes d'erreur à gérer côté handler** (extraits de [`Exception.php`](https://github.com/appwrite/appwrite/blob/30d6d252a726e74e9d3cd0ac1d10e8b0cddf731f/src/Appwrite/Extend/Exception.php) et [`app/config/errors.php`](https://github.com/appwrite/appwrite/blob/30d6d252a726e74e9d3cd0ac1d10e8b0cddf731f/app/config/errors.php)) :

| Code | HTTP | Signification |
|---|---|---|
| `transaction_not_found` | 404 | Transaction inconnue ou déjà nettoyée. |
| `transaction_already_exists` | 409 | Conflit de création. |
| `transaction_invalid` | 400 | Transaction invalide (p. ex. opérations visant des instances de base différentes — non pertinent pour un projet Cloud mono-instance). |
| `transaction_failed` | 400 | Échec générique à la validation/commit. |
| `transaction_expired` | 410 | TTL dépassé; il faut recréer une transaction. |
| `transaction_conflict` | **409** | Document modifié après la mise en file (concurrence optimiste); à relire et retenter. |
| `transaction_limit_exceeded` | 400 | Dépassement du plafond d'opérations du plan. |
| `transaction_not_ready` | 400 | Commit tenté trop tôt / état incohérent. |

**Nuance trouvée uniquement dans le code source, absente de la documentation publique** : toutes les opérations d'une transaction doivent cibler des bases de données hébergées sur la **même instance** de base de données sous-jacente, sous peine de `transaction_invalid` ([source `Update.php`](https://github.com/appwrite/appwrite/blob/30d6d252a726e74e9d3cd0ac1d10e8b0cddf731f/src/Appwrite/Platform/Modules/Databases/Http/Databases/Transactions/Update.php)). Cette contrainte concerne surtout les déploiements auto-hébergés avec plusieurs instances; elle n'a pas été vérifiée comme pertinente pour un projet Appwrite Cloud mono-base comme celui-ci, mais le point n'est documenté nulle part côté produit — à garder en tête si l'architecture d'hébergement changeait.

**Bénéfices mis en avant par Appwrite** (reformulation fidèle de l'annonce officielle) : garanties ACID sur les opérations mises en file (« Ensures atomicity, consistency, isolation, and durability »), absence de logique de rollback manuelle à écrire, retries plus sûrs car il n'y a pas d'état partiel, validation centralisée des permissions/conflits au moment du commit, et un mode de mise en file groupée adapté aux migrations/synchronisations ([annonce Appwrite](https://appwrite.io/blog/post/announcing-transactions-api)). La même source confirme explicitement : « The Transactions API is now available on Appwrite Cloud. »

## Pagination `listDocuments`/`listRows`

**Taille de page par défaut : 25.** Sans `Query.limit()` explicite, Appwrite renvoie 25 documents/lignes; ce nombre est ajustable, et **aucune limite maximale n'est documentée** côté produit, avec un avertissement explicite que de grandes pages dégradent les performances ([doc pagination](https://appwrite.io/docs/products/databases/documentsdb/pagination); confirmé aussi sur [doc requêtes TablesDB](https://appwrite.io/docs/products/databases/tablesdb/queries), redirigée depuis la page générique des requêtes). Inspection du validateur de requêtes sous-jacent : la classe `Limit` d'Utopia (bibliothèque base de données d'Appwrite) accepte un plafond configurable mais vaut `PHP_INT_MAX` par défaut ([source `Limit.php`](https://github.com/utopia-php/database/blob/950a4907d5519efd7ac7d1aff8978e482f8e07ae/src/Database/Validator/Query/Limit.php)), et les routes `listRows`/`listDocuments` d'Appwrite ne lui passent pas de plafond explicite ([source `Base.php`](https://github.com/appwrite/appwrite/blob/30d6d252a726e74e9d3cd0ac1d10e8b0cddf731f/src/Appwrite/Utopia/Database/Validator/Queries/Base.php)) — ce qui corrobore, sans le prouver de façon exhaustive (autres limites d'infrastructure possibles), l'absence de plafond annoncée par la documentation.

**Deux stratégies de pagination** ([doc pagination](https://appwrite.io/docs/products/databases/documentsdb/pagination)) :
- **Décalage** (`Query.limit()` + `Query.offset()`) : simple à indexer par numéro de page, mais plus lent à mesure que le décalage grandit, et peut produire des doublons ou sauter des résultats si des lignes sont insérées/supprimées entre deux pages consécutives.
- **Curseur** (`Query.cursorAfter(dernierId)` / `Query.cursorBefore(premierId)`) : recommandé pour les données fréquemment mises à jour ou en forte volumétrie — la documentation cite explicitement l'historique de chat comme cas d'usage typique. C'est directement transposable au fil mixte offres/messages de l'issue #27, qui grossit au fil des échanges.

**Options connexes utiles au design de l'infinite scroll** : le paramètre `total` (présent sur `listRows`, [source `XList.php`](https://github.com/appwrite/appwrite/blob/30d6d252a726e74e9d3cd0ac1d10e8b0cddf731f/src/Appwrite/Platform/Modules/Databases/Http/TablesDB/Tables/Rows/XList.php)) peut être mis à `false` pour ne pas calculer le total (coût de performance évité quand seul un prochain lot est nécessaire); un cache de réponse optionnel (`ttl`, de 0 à 86400 s, clé par projet/table/schéma/rôles/requête exacte) existe mais **les écritures n'invalident pas le cache** — un `ttl` non nul sur une liste d'offres/messages en cours de modification pourrait donc servir une page obsolète pendant la durée du TTL choisi.

## Zones d'incertitude et vérifications non faites

- Les limites par plan (Free = 100 opérations/transaction) proviennent de la documentation produit et du fichier de constantes source à la date de consultation; elles peuvent évoluer — à reconfirmer dans la console Appwrite si le comportement observé diffère.
- La restriction « même instance de base de données » n'a pas pu être testée en conditions réelles sur ce projet (Appwrite Cloud, projet mono-base) : elle est documentée uniquement dans le code source du serveur, jamais dans les pages produit.
- L'absence de plafond serveur sur `Query.limit()` est confirmée indirectement via le code des validateurs (`Limit`/`Offset` par défaut non bornés, et les routes de liste ne fixent pas de plafond explicite) en complément de l'affirmation claire de la documentation — mais aucun test d'abus réel (requête avec une limite extrême) n'a été exécuté contre une instance Appwrite Cloud.
- Cette note ne couvre pas si/comment la Transactions API interagit avec les déclencheurs d'événements (`queueForEvents`/`queueForRealtime`/webhooks) observés dans le code source du commit — ils apparaissent dans le flux de commit mais leur comportement exact (émis à chaque opération ou seulement après commit réussi) n'a pas été vérifié en détail et est hors du périmètre strict des deux questions posées.
